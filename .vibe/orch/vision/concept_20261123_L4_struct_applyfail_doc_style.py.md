## 지금 개념
개선안이 파일을 바꾸고 게이트(구문, run_all.js, 정의 정합)를 통과하면 그 시각 appliedMs 를 '반영 완료'로 적는다(orch-improve.js:315). VMO 는 이 시각을 결함을 고친 시점으로 삼아 재발 감시, L3 → L4 올림(orch-ladder.js:86-87, structWatchDays 3일), 7일 관찰을 센다. VM 코드가 실행 중 프로세스에 실리는 시점은 VS Code 창 다시 로드 뒤다(needsReload, orch-improve.js:315). 창 다시 로드는 VMO 가 하지 않는다. 판정을 내리는 VMO 코드(orch-ladder.js, orch-selfcheck.js)도 같은 규칙을 따르므로, 판정 코드를 고친 수정도 창 로드 전에는 판정에 쓰이지 않는다.

## 대안 개념
### A. 효력 기준 판정(반영 완료와 효력 시작을 나눔)
- 개선안 상태를 '반영 완료(파일)'와 '효력 시작(실행 코드에 실림)'으로 나눔. 효력 시각 = needsReload 면 appliedMs 뒤 첫 창 로드, 아니면 appliedMs. orch-ladder.js:64 effMsOf 를 공용 함수로 올리고 개선안에 effectiveMs 를 적음.
- 재발 감시(S8), L3·L4 올림, 7일 관찰, 반영 실패 집계는 효력 시각 뒤 근거만 셈. 효력 전이면 '로드 대기'로 보류하고 AI 진단을 부르지 않음.
- VMO 판정 코드가 설치본보다 오래됐으면(orch-improve.js:76 staleFiles) 그 코드가 만든 L3·L4 묶음은 '판정 코드 로드 대기'로 두고 AI 진단을 미룸.
- 사례 1, 3: 효력 전이라 올림 보류. 사례 4: 화면에 로드 대기 17건 표시. 사례 5: 고친 안의 효력 뒤 실패가 없으면 묶음 없음.
- 새로 할 일: effectiveMs 필드, 공용 함수, 판정 코드 판 확인, 개선안 탭과 Overview 표시. 버리는 것: appliedMs 를 고친 시점으로 쓰는 계산.
- 창 다시 로드를 자동으로 하지 않는다는 11-19 결정은 그대로.
### B. VMO 판정 모듈 즉시 다시 읽기
- orch-ladder.js, orch-selfcheck.js 같은 판정 모듈은 반영 뒤 require 캐시를 지우고 다음 tick 에 새 코드로 돎. 판정 모듈은 창 로드 없이 효력 시작.
- 사례 1, 3: 다음 tick 에 새 코드가 판정해 묶음 해소. 사례 4: 판정 모듈 몫만 풀리고 extension.js, workbench.js 같은 화면·실행 코드 몫은 로드 대기로 남음.
- 새로 할 일: 다시 읽을 모듈 목록, 모듈 상태(타이머, 열린 감시) 넘김, 실패 때 옛 모듈 유지. 버리는 것 없음.
- 위험: 새 orch-ladder.js 가 옛 orch-improve.js 를 부르는 판 섞임. 상태 넘김 결함이 VMO 정지로 이어짐. 시험 범위 미확인.
### C. 실행 중 작업이 없을 때 창 자동 다시 로드
- 체인, 업무 작업, CheckList 실행 0건이고 로드 대기 반영이 있으면 VMO 가 창 다시 로드를 실행.
- 사례 1, 3, 4 가 다음 빈 시간에 효력 시작.
- 11-19 사용자 승인 범위('VS Code 창 다시 로드는 자동으로 하지 않음')를 바꿈. 사용자가 VS Code 를 쓰는 중에 창이 다시 로드됨. 다시 로드 뒤 재개 문제 지적 U13, U16, U23 이력 있음.

## 권장안과 이유
A 를 권장함.
- 사례 1~5 에서 효력 전 수정을 고친 것으로 세지 않고, 효력 뒤 재발만 L3·L4 근거로 씀. 이번 같은 거짓 L4 올림과 그 AI 호출이 없어짐.
- 사용자 결정(창 다시 로드 자동 안 함)을 바꾸지 않음. C 는 그 결정을 바꿔야 함.
- B 는 판정 모듈만 풀고 화면·실행 코드 수정은 로드 대기로 남음. 판 섞임 위험의 시험 범위 미확인.
- 140537_VISION 이 L3 → L4 올림 한 곳에 효력 기준을 넣었음. A 는 이를 공용 개념으로 올려 재발 감시, 관찰, 반영 실패 집계, 표시에 같은 기준을 씀.
- B 는 A 전환 뒤 판정 모듈 한정 별도 안으로 남김.

## 전환(바뀌는 것 · 버리는 것 · 단계 · 확인 · 위험 · 되돌리기)
- 바뀌는 것: orch-improve.js(effectiveMs 기록, 공용 effMsOf, 개선안 탭 상태 '반영 완료, 로드 대기'), orch-ladder.js(:40 S8 floorMs, :53 반영 실패 7일 창, :86-92 공용 함수 사용), orch-selfcheck.js S8 재발 판정, Overview 진단 사다리 카드, 시험 t_orch_ladder.js, t_orch_improve.js.
- 버리는 것: appliedMs 를 고친 시점으로 쓰는 계산. 판정 코드가 설치본보다 오래된 상태에서 L3·L4 AI 진단을 부르는 동작.
- 단계 1: 공용 effMsOf 와 effectiveMs 필드. 확인 = 재현 시험(000421_SELF needsReload, appliedMs 11-22 00:21, 마지막 activations 11-21 01:59:17 입력 → effectiveMs 없음).
- 단계 2: 재발, 올림, 관찰, 반영 실패 집계를 effectiveMs 기준으로. 확인 = 사례 1, 3 근거를 넣은 scan() 결과에 L4|struct|applyfail|doc_style.py, L4|struct|edits|workbench.js 없음. 효력 뒤 새 반영 실패 2건을 넣으면 L4 올림 유지(반대 시험).
- 단계 3: 판정 코드 판 확인. staleFiles 에 orch-ladder.js 또는 orch-selfcheck.js 가 있으면 L3·L4 AI 진단 보류. 확인 = staleFiles 가짜 입력 시험에서 dayRuns 증가 0.
- 단계 4: 개선안 탭과 Overview 에 로드 대기 건수와 가장 오래된 대기 시각 표시. 확인 = 창 다시 로드 뒤 사용자 화면 확인.
- 위험: 사용자가 창을 오래 다시 로드하지 않으면 그동안 재발 감시가 보류됨. 대응 = 로드 대기 건수와 대기 시각을 카드에 표시. L2 사건 처리는 바꾸지 않음.
- 되돌리기: 단계마다 VMO 가 만든 .bak_<날짜>_self<시각> 사본 복원 또는 개선안 탭 되돌리기. effectiveMs 는 읽는 곳을 되돌리면 무시됨.

## 반증
- 다음 창 다시 로드 뒤 새 코드가 L4|struct|applyfail|doc_style.py 를 다시 올리면 원인은 효력 시각이 아님. 확인 = 로드 뒤 ladder.json 해당 묶음 why 문구와 status.
- 11-22 00:21 뒤 doc_style.py 대상 '반영 실패.' 기록이 생기면 구조 개선안이 효력을 못 낸 것임. 11-23 00:06 조회 0건.
- 실행 중 코드가 설치본과 같은 판이면(로드 기록 누락) 사례 2 가 틀림. 확인 = 창 로드 뒤 orch-improve.js code.staleFiles 측정값. 이 측정을 넣은 130655_REVIEW 도 로드 대기라 지금 실행 중 집계에는 없음.
