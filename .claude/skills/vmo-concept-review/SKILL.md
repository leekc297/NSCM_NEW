# VMO 개념 재정립

같은 목적이 구조 개선 뒤에도 계속 어긋나면 문제는 구현이 아니라 개념에 있다. 예를 들어 '중지 뒤 계속 실행을 잡는다'는 규칙이 재개된 실행을 계속 멈춘다면, 고칠 것은 판단 조건이 아니라 '중지'와 '재개'를 무엇으로 구분하는가라는 개념이다. 이 스킬은 개념을 목적에서 다시 세우는 순서와 결과 형식을 정한다.

## 순서

1. **목적 다시 읽기.** 목적 문서(메모리 feedback_*·project_*, tools/VibeManager/user_checks.json 의 사용자 원문, 플랜 파일)에서 이 묶음과 관계된 사용자 원문을 그대로 인용한다. 요약하지 않는다.
2. **지금 개념을 한 문단으로.** 지금 코드가 실제로 하는 일을 '무엇을 위해, 무엇을, 어떤 기준으로' 형식으로 적는다. 근거 파일:줄을 붙인다.
3. **어긋난 근거.** 목적과 지금 개념이 어긋난 사례를 표로 놓는다. 사례마다 사건·장부·판정 이력 줄을 근거로 단다. L3 에서 고친 이력과 그 뒤 재발도 넣는다.
4. **대안 개념 2개 이상.** 각 대안이 목적을 어떻게 충족하는지, 어긋난 사례가 대안에서는 어떻게 되는지, 무엇을 새로 해야 하고 무엇을 버리는지 적는다.
5. **권장안.** 하나를 고르고 이유를 적는다. 고르지 못하면 '사용자 판단 필요'와 판단에 필요한 질문 1개.
6. **전환.** 바뀌는 파일·규칙·설정, 버리는 것, 단계별 전환 순서, 단계마다 확인 방법, 위험, 되돌리는 법.
7. **반증.** 권장안이 틀렸다면 무엇이 보여야 하는지 적는다.

## 결과 문서 형식(.vibe/orch/vision/concept_<yyyymmdd>_<묶음 key>.md)

```
# 개념 재정립: <대상>
## 목적(사용자 원문)
## 지금 개념
## 어긋난 근거
| 사례 | 근거 | L3 조치 | 그 뒤 |
## 대안 개념
### A ... ### B ...
## 권장안과 이유
## 전환(바뀌는 것 · 버리는 것 · 단계 · 확인 · 위험 · 되돌리기)
## 반증
## 미확인
```

## 개선안

- 1건만 올린다. impact = core, level = L4, 제목 '개념 재정립: <대상>'.
- before_after 에 지금 개념 → 새 개념을 한 문장씩.
- plain 에 업무 말로 무엇이 달라지는지, 위험, 되돌리는 법.
- 승인 뒤 전환은 writing-plans 스킬로 실행 계획을 만든다(이 단계에서는 계획을 쓰지 않는다).

## 지킬 것

- 읽기만 한다. 파일을 고치지 않는다(결과 문서는 VMO 가 쓴다).
- 사용자 원문을 바꾸거나 요약해 근거로 쓰지 않는다.
- 감·예측 금지. 확인 못 한 것은 '미확인'.
- 문장은 한국어 업무 문서 문체(수식어, 번역투, 줄표 금지). 사용자 원문 인용은 그대로.
