## 1. 결론

**`optimizer_dynamic_sampling = 0`** (클라우드) 이 원인입니다. 사내는 **2**(Oracle 기본값)입니다.

DMF0082 조회는 중간 결과를 **GTT 에 단계적으로 적재**하는 구조인데, GTT 는 통계가 없습니다(사내 실측: GTT 2,388본 중 **2,386본이 통계 없음**). 통계 없는 GTT 의 카디널리티는 **동적 샘플링(dynamic sampling)** 으로만 추정되는데, 클라우드는 이 기능이 **꺼져 있습니다**. 그래서 옵티마이저가 행수를 크게 잘못 잡고 **Nested Loop** 를 선택 → 단일블록 랜덤 IO 가 폭증합니다.

## 4. 조치 (`04_ROOTCAUSE_FIX.sql`)

| Step | 내용 | 위험 |
|---:|---|---|
| **1** | **세션 레벨 증명** — 같은 세션에서 `ALTER SESSION SET optimizer_dynamic_sampling=2` 후 재조회, 시간 비교 | **없음** (세션 한정) |
| **2** | 효과 확인 시 `ALTER SYSTEM SET optimizer_dynamic_sampling=2 SCOPE=BOTH` | DBA 승인 필요. RAC 전 노드 반영 확인 |
| 3 | 시스템 변경 불가 시 대안 — GTT `GLOBAL_TEMP_TABLE_STATS='SESSION'` 또는 SP 도입부 `ALTER SESSION` | 별건 검토 |

⭐ **Step 1 을 먼저 하십시오.** 시스템을 건드리지 않고 원인을 확정할 수 있고, 효과가 없으면 제 진단이 틀린 것이므로 다시 봐야 합니다.
계획을 새로 세우게 하려면 기존 커서를 버려야 합니다 — `ALTER SYSTEM FLUSH SHARED_POOL` 이 부담되면 스크립트의 `DBMS_SHARED_POOL.PURGE` 로 해당 SQL_ID 2건만 제거하십시오.

## 5. 파급 — DMF0082 만의 문제가 아닙니다

`optimizer_dynamic_sampling=0` 은 **인스턴스 전역** 설정입니다. NSCM 의 SP 들은 대부분 GTT 로 중간 결과를 단계 적재하는 동일 구조이므로, **클라우드의 다른 화면들도 같은 이유로 느릴 가능성이 높습니다.**

Step 2 를 적용하면 전 화면이 함께 개선될 수 있습니다. 반대로, 지금까지 "클라우드만 느리다"고 보고된 다른 화면이 있다면 같은 원인일 수 있으니 함께 재측정해 보시길 권합니다.
