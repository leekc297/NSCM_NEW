## 3. 참고 — 병목 구간의 실측 성격

### 3-1. `TEMP_FCST_N_PRICE` (5.88초, 39%)
- INSERT 4회로 **357,980행** 적재 → DELETE 로 **297,826행** 제거 → MERGE 로 38,916행 갱신
- **이 "넣고 지우기"는 낭비가 아닙니다.** L967 주석대로 `LOC/KRW/FCST_GAP` 등 **계산에 필요한 measure 를 `USER_ID='DM_ADMIN'` 태그로 강제 포함**시킨 뒤(L968), 중간 계산(L2678 환율 MERGE, L2754 LOC/KRW, L2788 FCST_GAP)에 사용하고 마지막에 제거하는 구조입니다.
- 따라서 INSERT 시점 필터링은 **결과를 바꿉니다**. 손대려면 중간 계산 경로를 함께 재설계해야 합니다.

### 3-2. 동적샘플링 2.19초 / 16회
- `/* SQL Analyze(0) */ select /*+ full(t) no_parallel(t) ... */` — 옵티마이저가 통계 부족 객체를 **런타임에 풀스캔 샘플링**
- 논리읽기 78,384 · 물리 3,860 을 쓰고 **산출은 16행**(샘플 결과)

### 3-3. `MF_SP` INSERT (1.36초) — 대기가 대부분
- 초 1.36 vs **CPU 0.39** → 약 1초가 대기. 논리읽기 983 으로 매우 적음 = `APPEND` 직접경로 동작 중
- 60,154행 적재. `PARALLEL(4)` 힌트가 GTT 에서 실제로 병렬 동작하는지는 별도 확인 필요

### 3-4. 원천 테이블 과다 읽기 (참고)
`statistics_level=ALL` 실측 A-Rows 기준:

| 문장 | 읽은 행 | 산출 행 | 접근 |
|---|---:|---:|---|
| `T_LAST_DATA_SETUP_PRICE` | 510,000 | 5,877 | `TABLE ACCESS FULL DM_PLN_CFM_SELLING_PRICE` |
| `T_LAST_DATA_SETUP_FCST` | 74,037 | 2,737 | `TABLE ACCESS FULL DM_PLN_CFM_MKT_DEMAND_PLAN` |

- 감소분은 **`GROUP BY` 집계**입니다(HASH JOIN 출력이 505,000행 — 조인은 거의 안 거름). `MAX(CREATION_DATE)` 산출에 그 행들이 실제로 필요합니다.
- 다만 **테이블 전체 1,651,396행을 풀스캔해 div40+기간 510,432행을 얻는 3.2배 과다 읽기**는 있습니다. 두 테이블 모두 **인덱스가 PK 1본뿐**이고, PK 선두가 `DIVISION_ID, PROJECT_CODE, END_CUSTOMER, ...` 라 `YYYYMMDD` 조건을 못 씁니다.
- ⚠️ 다만 이 두 문장의 실측 비용은 **0.47초 / 0.11초**로 작습니다. 인덱스를 추가해도 절감폭은 제한적입니다.
