## 3. 조치 — 파티션 프루닝 조건 추가

### 3-1. 결과 불변 근거 (실측)

| 검증 | 결과 |
|---|---|
| `VERSION_NO` ↔ `CUTOFF_YYYYMMDD` 1:1 | 사내 **전 division 87 버전** — CUTOFF 다중 **0건** |
| `CUTOFF_YYYYMMDD` = `VERSION_NO` 의 8자리 | 불일치 **0건** |
| `DM_MST_VERSION.YYYYMMDD` = `CUTOFF_YYYYMMDD` | **81/81 일치**, 불일치 0 |

이미 `V.VERSION_NO = A.VERSION_NO` 조인이 있으므로, **조인을 통과하는 모든 행의 CUTOFF 는 반드시 선택 버전들의 CUTOFF 범위 안**에 있습니다. 따라서 추가 조건은 **행을 하나도 걸러내지 않고** 프루닝만 유도합니다.

### 3-2. 변경 내역 — 3지점 / +22 라인

| 지점 | 위치 | 내용 |
|---|---|---|
| 선언 | L174 직전 | `V_CUTOFF_FROM` / `V_CUTOFF_TO VARCHAR2(8 CHAR)` |
| 값 설정 | L385 직후 (T_VERSION 적재 완료 지점) | `SELECT NVL(MIN(B.YYYYMMDD),'00000000'), NVL(MAX(B.YYYYMMDD),'99999999') INTO ... FROM GT_DMF0082_T_VERSION V JOIN DM_MST_VERSION B ON B.VERSION_NO=V.VERSION_NO AND B.DIVISION_ID=p_division_id` |
| 조건 | **4곳** (L1126 / L1983 / L2415 / L2542) | `AND A.CUTOFF_YYYYMMDD BETWEEN V_CUTOFF_FROM AND V_CUTOFF_TO` |

조건 4곳은 **`SCM_MST_FUTURE_PRICE_C` 를 읽으면서 `GT_DMF0082_T_VERSION` 과 `VERSION_NO` 로 조인하는 문장 전부**입니다(전수 확인 — 이 테이블을 읽는 FROM 은 L1118/1961/2392/2520 4개뿐).

**NULL 가드**: 버전 0건이면 `NVL` 로 `'00000000'~'99999999'` → 기존과 동일 동작(어차피 조인에서 0행).

## 6. 남은 개선 여지

`L1983 / L2415 / L2542` 문장은 각각 `F.VERSION_NO LIKE 'MF%' / 'SF%' / 'SP%'` 로 **버전 타입을 한정**합니다. 그런데 `V_CUTOFF_FROM/TO` 는 **전체 버전**의 min/max 라, 타입별 실제 범위보다 넓습니다.
→ **결과는 불변이고 프루닝도 되지만 최적은 아닙니다.** 효과 측정 후 필요하면 타입별 변수(`V_CUTOFF_MF_FROM/TO` 등)로 세분화할 수 있습니다.

그리고 다른 `_C` 테이블(`DM_PLN_MKT_FCST_C`, `DM_PLN_CFM_MKT_DEMAND_PLAN_C`, `DM_PLN_SALES_PLAN_RESULT_C`, `DM_PLN_CFM_SELLING_PRICE_C`, `DM_PLN_MKT_FCST_RESULT_C`)도 클라우드에서 파티션되어 있다면 같은 조치가 필요합니다. 클라우드에서 확인 후 별건 진행 권고.

## 7. GTT 인덱스 — 실측 결과 **불필요** (별도 요청 건)

실행계획 기반으로 GTT 접근 방식을 조사한 결과:

| GTT | 풀스캔 | Starts | 누적 스캔행 | 조건컬럼 |
|---|---:|---:|---:|---|
| `GT_DMF0082_TEMP_SITE_ITEM` | 4 | **2** | 29,612 | DIVISION_ID |
| `GT_DMF0082_T_VERSION` | 4 | **4** | 0 | — |

둘 다 **`HASH JOIN` 의 build/probe side 로 full scan** 되며 **Starts 가 2~4** 입니다(반복 probe 아님).
**HASH JOIN 은 인덱스를 사용하지 않으므로** 인덱스를 만들어도 옵티마이저가 쓰지 않고, 대량 INSERT(`TEMP_FCST_N_PRICE` 357K행 등)에 유지 비용만 추가됩니다.
클라우드 계획에서도 동일 — `TABLE ACCESS STORAGE FULL GT_DMF0082_TEMP_SITE_ITEM` Cost **242** vs 68M 테이블 접근 Cost **189K**(0.1% 수준).

→ **GTT 인덱스는 생성하지 않았습니다.** 효과 없는 변경으로 INSERT 를 느리게 만들 이유가 없습니다.
