## 1. [항목3] `(p_xxx='ALL' OR ...)` 20곳 — **무변경 판정** ✅

### 실측 (사내 div40, 동일 조건)
| 시나리오 | wall | LR | rows |
|---|---:|---:|---:|
| site = ALL | 13.09초 | 1,084,754 | 1,974 |
| site 2개 선택 | **2.81초** | 238,258 | 37 |
| site 4개 선택 | **3.84초** | 303,706 | 37 |

### 판정 근거
- **ALL 인 경우**: `filter(:B='ALL' OR ...)` 는 OR **단락평가** — 첫 항이 TRUE 라 `CONNECT BY` 서브쿼리가 아예 실행되지 않음. 비용 0.
- **멀티선택인 경우**: 첫 단계(`TEMP_SITE_ITEM_ALL`)부터 기준집합이 축소되어 **전체가 3~5배 빨라짐**. FILTER 형태여도 서브쿼리 캐싱으로 행별 비용 미미.
- 인덱스 접근 관점: 이 술어가 걸리는 문장들의 접근은 `DIVISION_ID` + 파티션 프루닝 + 버전 조인이 주도. `SCM_SITE_ID` 는 부가 필터라 access 로 승격해도 이득 없음.
- → 21개 문장 수정은 **이득 0 / 결과 변경 리스크만 존재** → 하지 않음.

### 참고 (측정 중 확인)
- 파라미터 순서: **P2=TEAM, P7=SCM_SITE** (P2 에 사이트를 넣으면 조용히 무시됨)
- 사이트 필터의 유효값은 **`SITE_TYPE='SALES'` 사이트만** (`NJ01-A` 같은 plant 계열은 L822 INNER JOIN 에서 전멸 → 결과 0행)

## 4. 남은 시간의 실제 구조 — [항목5] 표적 (실측)

3. 통계 호출 합리화 — 효과 대비 카디널리티 품질 리스크 있어 후순위.
