## 1. 목적과 원칙

- **미실행 = 검증하지 않은 행**이다. PASS 로 세지 않는다. 화면 완료 판정에서는 "미검증 잔여"로 따로 보고한다.
- 목표는 미실행을 **사유가 있는 소수**로 줄이는 것이다. 남는 행은 모두 이유와 처리 계획을 가진다.
- 미실행을 판정으로 바꿀 때는 **정답(oracle)을 먼저 정하고** 검사기를 만든다. 정답이 없으면 `판정필요`로 둔다. 추측 PASS 는 금지한다.
- **AS-IS 비교는 같은 데이터 위에서 한다.** AS-IS DEV DB(LGCE_SCMDEV)와 사내 TO-BE DB 는 데이터가 다르다. 그래서 건수를 서로 비교하지 않는다. AS-IS 원문 논리(SP 분기·필터식)를 TO-BE 데이터에 적용해 기대값을 만든다.
  - 2026-10-24 SCP0007 To Site 8조합 확정에 쓴 방식이다.
- 실제 저장은 한다(사용자 지시 2026-10-23). 단, **신규 마커 행만** 쓴다. 기존 원장 행은 덮어쓰지 않는다. 저장한 행은 백업 후 정리하고 정리 SQL 을 남긴다(§5).

### W1. AS-IS 원천 비교 엔진 (콤보·조회 건수)

- **정답**: TO-BE 콤보 메타 `SCM_ADM_CMBO_SQL_M.SQL_NM` 에 적힌 AS-IS 원천(`@Code='ToSiteBOD1'` 등)이다. 이 원천의 AS-IS SP 분기 원문을 TO-BE 데이터에 적용해 기대 후보 집합을 만든다.
  - 조회 건수(A1)는 FE 가 실제로 보낸 인자를 `param_map` 으로 AS-IS 인자로 바꿔 실행한 결과와 비교한다.
- **방법**: E2E 에서 셀·조회조건 콤보 후보(`getDisplayValues`)를 읽고, 같은 시점에 기대 집합을 계산해 차집합(추가·누락 목록)을 증거로 남긴다.
- **함께 해결**: C2 "후보 동일" 판정필요는 분기별 기대 집합이 같으면 PASS, 다르면 FAIL 로 자동 판정한다.
  - 2026-10-24 SCP0007 수동 확정 7건을 자동으로 바꾼다.
- **선행**: AS-IS SP 원문 분기 추출기(`UP_FX_GetCommonDataList_*` 코드별 SELECT 를 Oracle 로 옮긴 것은 TO-BE 메타에 이미 있다). AS-IS 화면의 `DBUtils.Filter` 필터식 리터럴 보존(P1 잔여).

### W2. 행 조건 계산기 (조건부 잠금·편집 구간)

- **정답**: AS-IS 잠금 guard 를 행 값으로 계산한 결과다.
- **현재 한계**: 지역 변수(`strTO_SITE_TYPE` 등)를 룩업으로 풀지 못해 `판정필요`가 된다.
- **방법**:
  1. guard 의 지역 변수가 대입되는 문장을 `actions.csv` 에서 추적한다(`dr["SITE_TYPE"]` ← `dtToSiteOfSpd.Select("CODE=…")`).
  2. 그 원천을 W1 엔진으로 조회해 행별 값을 얻는다.
  3. Edit 버튼 모드(`boolEditChange`)는 실제로 Edit 를 눌러 두 상태를 각각 프로브한다.
- **대상**: D3 315행, D1 Edit 모드 행, D2 Measure×기간, J3 권한별 편집 구간, H2 상태별 배경색.

### W3. 위반 입력·저장 시나리오 (업무 검증·붙여넣기·팝업 CRUD·업로드)

- **정답**: AS-IS VALIDATE·MESSAGE 사실(조건 + 메시지 ID)과 TO-BE 메시지 매핑(msgmap, 문구 기준)이다.
- **방법**: 조건을 일부러 위반하는 값을 넣고 저장한다. 같은 의미의 메시지가 나오고 저장이 차단되는지 본다(E4).
  - 붙여넣기 경로(F3)는 클립보드 붙여넣기로 같은 연쇄·저장을 확인한다.
  - 팝업 내부 조회·저장(M3)·Excel 업로드(M1)·특수 버튼(M2)은 기능별 시나리오로 실행한다.
- **DB**: 정상 저장 경로는 마커 행으로만 실행하고 §5 정리 절차를 따른다.
- **선행(DM 화면)**:
  - DMF0082 CRUD 는 기간별 수량 칸을 채워야 저장된다("수량 또는 가격 필요" 검증).
  - DMF0005 CRUD 는 필수 컬럼을 찾지 못해 즉시 종료됐다. 원인 확인이 필요하다.

### W4. 공통 기능 1회 + 화면 연결

- Sort/Filter·컬럼 셋팅·Excel 다운로드·셀 병합·레이아웃·성능 같은 공통 기능은 화면마다 반복 실행하지 않는다.
  1. **공통 컴포넌트 기준 화면 1개**에서 결과까지 판정한다.
  2. 다른 화면은 "그 공통 컴포넌트를 쓰는가 + 화면별 설정(메타)이 기준과 같은가"만 확인한다(STATIC+META).
  3. 화면이 공통 컴포넌트를 쓰지 않으면 그 화면만 E2E 로 판정한다.
- **행 유형 확장**:
  - 조회조건 팝업(G5·H6: City 팝업 등)
  - 단일선택·텍스트 조회조건(G1·G2: 대소문자 무관·부분일치·콤마 다중)
  - 조회조건 cascade(C1)
  - 조회조건 저장·복원(G3)
- 공통 컴포넌트 결함은 `repairScope` 와 관계없이 **가이드만** 남긴다(공통 수정 금지 원칙).

### W5. 권한·메타·확정 규칙 연결

- 권한별 CRUD(5축)는 `users.json` 계정 풀에서 영역 ADMIN 1명과 권한 없음 1명으로 실행한다.
  - 확인 항목: Division 노출(J1)·버튼(J2)·메뉴 노출(J4)
- 메타 전용(N1 기준데이터 공란 혼재, B8 원천 표준, I4 중복 채번)은 사내 DB 쿼리로 판정한다.
- 고객 확정 규칙(CONFIRMED) 미실행 행은 일반 규칙을 그 화면 요소에 연결하는 매핑표를 만들어 해당 단계 검사기로 넘긴다.
  - 예: "모든 팝업 OK→CLOSE" → 이 화면의 팝업 목록

## 5. 실제 저장 행 관리 (CRUD·W3 공통)

1. 저장 전: 마커 값(`E2E_<MMDDHHmm>`)을 비고 류 칸에 넣는다. 팝업·연쇄 대상 칸은 쓰지 않는다.
2. 저장 후: 화면에서 삭제할 수 있으면 화면에서 삭제·저장한다.
   - 못 하면(예: BOD — AS-IS 도 신규행만 삭제) 원장에 `정리 필요`를 남긴다.
3. 정리: 아래 순서로 한다.
   1. 생성 시각 + 생성자 + 마커로 대상 행을 특정한다.
   2. 연쇄 생성 행(이력·아이템)까지 CSV 로 백업한다.
   3. 건수를 단언한 뒤 DELETE 한다. 기대 건수와 다르면 ROLLBACK 한다.
   4. 잔존 0 건을 확인한다.
   5. `Doc/verify/<ID>/cleanup_*.sql` 에 기록한다.
   - 실례: SCP0007 BOD_ID 20945·20950. 이력 테이블에 같은 BOD_ID 의 과거 이력(9/18 타 사용자)이 있어, 시각·마커 조건으로 보존했다.
4. 다음 단계: 정리를 `run_verify.py` 후처리로 자동화한다(대상 테이블 = 저장 SP 의 DML 대상, `ui_save_dml_tables` 산출물 재사용).

## 6. 완료 기준

- 시범 3화면에서 미실행 사유 코드 누락 0 (V-NR1).
- 단계마다 해당 규칙의 미실행 → PASS/FAIL/판정필요 전환을 확인한다. 같은 빌드 2회 실행 결과가 같아야 한다.
- 결함 원장 310건: 규칙 대응 310/310 은 이미 충족했다. **실행 대응**(그 결함 패턴의 행이 실제로 실행됨)을 단계별로 늘려 W5 종료 시 310/310 을 목표로 한다.
  - 실행이 끝내 불가한 건은 사유와 함께 별도 보고한다.
- 과거 빌드 실증: 단계마다 유형별 대표 결함 1~2건이 조치 전 커밋에서 FAIL 로 나와야 한다.
- 판정필요는 사람판정 목록(`보완대상_v<N>.xlsx` 사람판정 시트)으로 넘기고, 확정 결과는 `tobe_ref='수동 …'` 으로 원장에 남긴다. 수동 판정은 자동 재실행이 덮어쓰지 않는다(2026-10-24 judge 반영).
