# Hook #137 — oracle-load-dedup-and-exception-propagation ⭐⭐⭐ (2026-08-18 DMF0014 실사고 계기 신설)

> **트리거**: 원장 적재 SP 작성·변환·보완 전부 (`INSERT ... SELECT` / `MERGE` 로 PK 있는 표에 적재).
> **한 줄**: ① **`SELECT DISTINCT` 는 중복 제거 수단이 아니다** — 감사·시각 컬럼이 섞이면 무력화된다.
> PK 가 있으면 **PK 기준 dedup** 을 명시하라. ② 하위 프로시저의 **`WHEN OTHERS THEN ROLLBACK`** 은
> 호출자 트랜잭션까지 되돌리고 정상 종료해 **허위 성공**을 만든다 — `RAISE` 로 전파하라.
> **연관**: #99 · #127(NVL 안티패턴) · #131(저장 멱등·읽기검증) · save-sp-direct-call-commits

## §1 사고 계보 (2026-08-18, DMF0014 Excel Upload)

동일 파일 2회차 저장이 `ORA-00001`(`PK_DM_PLN_MKT_FCST`) 로 실패했다. **원인 규명에 5회 실패**한 뒤
계측(진단표에 적재 소스 전 컬럼 스냅샷)으로 확정한 사실:

> 중복 4행이 갈라지는 컬럼은 **`CREATION_DATE` 단 하나**. PK 10키와 나머지 전 컬럼은 완전히 동일.
> 1회차 저장이 남긴 원장(PSI) 행과 2회차 업로드 행이 같은 대상인데 **생성시각만 달랐고**,
> 적재 쿼리의 `SELECT DISTINCT` 목록에 그 컬럼이 있어 **접히지 않은 채 둘 다 INSERT** 됐다.

그 전까지 손댄 3건(선삭제 범위 일치 / INSERT→MERGE 전환 / `SYSTIMESTAMP` 를 DISTINCT 밖으로)은
전부 증상을 없애지 못했다 — **추정으로 좁히면 계속 빗나간다**는 것이 이 사고의 교훈이다.

## §2 규칙 A — 적재 소스의 유일성은 **PK 기준으로 명시**한다

| # | 규칙 |
|---:|---|
| A1 | 대상 표에 PK/UNIQUE 가 있으면, 소스는 **그 키 기준으로 1행**임을 보장해야 한다. `SELECT DISTINCT` 는 **선택목록 전체**가 같아야만 접히므로 보장 수단이 아니다 |
| A2 | `SELECT DISTINCT` 안에 **`SYSDATE`/`SYSTIMESTAMP`/`CREATION_DATE`/`LAST_UPDATE_DATE` 같은 시각·감사 컬럼 금지**. 상수·시각은 **바깥 SELECT 에서** 부여한다 |
| A3 | 그래도 PK 중복이 남을 수 있으면 **`ROW_NUMBER() OVER (PARTITION BY <PK 전 컬럼> ORDER BY <결정적 정렬>) = 1`** 로 1행 확정. 정렬 기준은 **근거를 주석에 남긴다**(예: 최신 업로드분 우선 = `CREATION_DATE DESC`) |
| A4 | ⚠ 윈도우 함수는 `WHERE` 에 직접 못 쓴다(`ORA-30483`) — 인라인뷰 SELECT 에서 `RN` 을 만들고 **바깥에서 `WHERE RN = 1`** |
| A5 | ⚠ 조인 양쪽에 같은 컬럼명이 있으면 `PARTITION BY` 도 **별칭 한정** 필요(`A.MEASURE` — 무한정 시 `ORA-00918`) |
| A6 | 선삭제를 둔다면 **삭제 범위 = 삽입 범위**(같은 소스·같은 조건). 범위가 다르면 안 지워진 행과 충돌한다 |

## §3 규칙 B — 예외는 삼키지 않는다

| # | 규칙 |
|---:|---|
| B1 | 하위 프로시저의 `EXCEPTION WHEN OTHERS THEN ROLLBACK;` 은 **호출자가 같은 트랜잭션에서 넣은 행까지 되돌린다**. 그리고 정상 리턴하므로 호출자는 성공으로 착각한다 |
| B2 | 로그를 남긴 뒤 **반드시 `RAISE`** 로 전파한다. 실패는 실패로 끝나야 한다 |
| B3 | 적재 SP 말미에는 **원장 재확인 가드**(적재 건수 + 실제 잔존 행수)를 둔다 — 하위가 롤백해도 잡힌다(#131 계열) |
| B4 | 가드가 잡은 오류를 "가드 오탐" 으로 넘기지 말 것. 2026-08-18 실측에서 `Save verify failed (inserted=15, persisted=0)` 는 **정확한 보고**였고, 실제로 롤백이 일어나고 있었다 |

## §4 규칙 C — 원인 규명은 계측으로 확정한다

이 사고에서 추정 5건이 연속으로 빗나갔다(SPLIT 수렴 → 선삭제 범위 → 소스 PK 중복 → DISTINCT 무력화 → 이중 호출).
**세션 전용 GTT 는 실패한 세션과 함께 사라지므로** 로그만으로는 못 잡는다.

1. 실패가 재현되는 **결정적 경로**를 먼저 확보한다(예: 같은 파일 1회차 성공 → 2회차 실패).
2. 적재 직전 소스를 **영구 진단표에 전 컬럼 스냅샷 + `COMMIT`** 으로 남기는 임시 계측을 심는다.
3. 실패를 재현해 **어느 컬럼이 갈라지는지 컬럼 단위로 확정**한 뒤에만 코드를 고친다.
4. 원인 확정 후 **계측은 반드시 제거**한다(진단표도 정리).

> ⛔ 계측 없이 "아마 이것 때문일 것" 으로 코드를 고치고 배포 → 재실패 → 또 추정, 을 반복하지 말 것.
> 배포마다 객체가 INVALID 로 떨어질 위험을 지므로(#136) 시도 횟수 자체가 리스크다.
